# Decisions

## 2026-10-17 — LOOPKEEPER V9: Natural-Language Crisis Launcher, Live Robot Autonomy, and Non-Destructive Manual Drive

1. **Deterministic ScenarioCompiler as Autonomous Firewall:** LLMs (Crusoe Nemotron) and classification models (Laya) are strictly prohibited from mutating physics matrices or injecting untested actuator commands directly. Instead, `ScenarioCompiler` acts as a deterministic compiler that parses model output into verified `ScenarioDefinition` records with exact topology localization, declared assumptions, and 3 measurable `DefinitionOfDone` invariants.
2. **Non-Destructive Ghost Preview Drive vs Authoritative Live Lease:** To give operators spatial intuition without disrupting mission-critical autonomous maintenance, Preview Drive instantiates a purely local visual ghost proxy (`GhostRobotOverlay.tsx`, `usePreviewDrive`). Arrow keys / WASD steer the ghost along graph corridors with **zero network traffic, zero lease requests, and zero database writes**. Exiting preview cleanly removes the ghost and restores authoritative view. Live robot teleoperation remains strictly gated behind server-authoritative leases with deadman switches.
3. **Truthful Provider Fallback Over Synthetic Mocking:** In accordance with the hackathon's "Done Means Done" standard, when Crusoe Managed Inference returns HTTP 402 ("Organization has no valid payment method"), the system never produces fake completions. It transparently logs `fallback_active: True`, utilizes `deterministic-semantic-parser-v1`, and records exact token metrics into Neon PostgreSQL.
4. **Asynchronous Outbox Job Execution for Scenario Launch:** Scenario creation is decoupled from browser request lifecycles. `POST /api/v1/scenario-requests` durable enqueues a job into Neon PostgreSQL outbox and returns HTTP 202 Accepted within 40ms. The background worker asynchronously executes Laya classification, Crusoe parsing, deterministic compilation, and 30-minute episode recording, allowing the UI to render real-time multi-phase lifecycle progress without HTTP timeouts.


1. **Vite + React instead of Next.js** — a pure SPA with a canvas; deployment is a static folder (frontend-ui.md §4 allows it).
2. **One 3D scene for web and native** (`packages/scene`) using only three + @react-three/fiber. Platform-specific code is limited to input and DOM chrome.
3. **Store-driven camera.** Inputs write a *goal*; one rig eases the real camera, applies a safe-area view offset (so focus never hides behind a panel) and switches to first-person/section views inside pipes.
4. **Dev simulator behind the real contract.** `apps/mock-api` exists so web and phone develop against a real network boundary and show the *same* world; `EmbeddedTransport` runs the same engine in-page for zero-setup demos. The engine reports `backend: "mock"` and the UI labels it.
5. **Counterfactual verification.** The verifier compares against the twin with only *this* incident's fault removed, so concurrent faults don't corrupt each other's verdicts; thermal margin is judged at nominal load.
6. **Redundant meters for hydraulic residuals.** ΔP-vs-flow uses rack meters, not a possibly-drifting header meter.
7. **Escalation is a first-class state** (`escalated`), not a silent loop.
8. **Pipe exaggeration only in overview.** Outer pipe radius is scaled ×1.75 for legibility; the inside of a pipe and the crawler use the true bore.
9. **No audio alarms, no modal cascades.** One pinned incident card; severity is colour *and* text.
10. **Replay pauses live application** rather than shadowing it, so replay cannot alter the authoritative world; a fresh snapshot is fetched on return.

## 2026-10-17 — LOOPKEEPER V8: Crisis Execution Lab & 30-Minute Counterfactuals

11. **Server-Authoritative Fluid Leak Model (`CR-02`):** Rather than omitting the leak or producing disconnected particle effects, `leak_model.py` provides a conservative Torricelli orifice discharge model ($C_d = 0.62$) coupled to loop pressure derating and floor puddle spreading ($5\text{mm}$ thin-film). Playback speed controls (1×, 2×, 3×) pace execution faithfully without skipping solver iterations or inventing frames.
13. **Reversible Hide/Collapse Overlays:** All overlay panels in the Execution Tab (Scenario Library, Runs Panel, Run Inspector, Timeline) are managed via `ExecutionPanelsStore` with close buttons (`×`), persistent top/icon rail toggles, and keyboard `Esc` handling. Collapsing panels leaves the 3D viewport 100% unobstructed without unmounting or terminating active simulation runs.
14. **Truthful Browser-GPU Progressive Rendering:** Remote WebRTC streaming is not claimed because the host binary of `ffmpeg` lacks NVENC hardware encoding. The verified rendering path is browser-GPU execution via React Three Fiber and Three.js with geometry instancing and progressive caching.
15. **Independent Verification & Verdict Integrity:** Every scenario verdict is evaluated against ground-truth multi-physics equations (solver convergence, mass and energy conservation, thermal limits, and safety invariants). Premature or sensor-biased recovery claims (such as in `CR-07`) are strictly rejected.

## 2026-10-17 — Dual Neon Database Coexistence Architecture (Control Plane vs. Telemetry Lake)

95. **Dual Neon Database Architecture (`loopkeeper-control` & `loopkeeper-telemetry`):**
    - **Problem**: In high-fidelity 2 Hz simulation runs, high-frequency sensory telemetry (`sensor_samples`, `world_snapshots`, `world_events`) produces hundreds of thousands to millions of time-series records per run. Performing bulk inserts and compactions in the same PostgreSQL database that handles ACID transactional control (leases, operator commands, multi-agent runs, incident state, and LangGraph checkpointer advisory locks) risks table lock contention, storage quota exhaustion (1 GB limit on Neon projects), and jitter on single-writer simulation ticks.
    - **Architecture Decision**: Split database persistence into two distinct, coexisting Neon projects:
      1. `loopkeeper-control` (`DATABASE_URL`, project `flat-lake-30099482`, `aws-us-west-2`): Dedicated Transactional & Agent Control Plane. Owns `facilities`, `simulation_runs`, `commands`, `missions`, `robots`, `incidents`, `control_leases`, `traffic_reservations`, `agent_runs`, `verification_runs`, and LangGraph checkpoints (`checkpoints`, `checkpoint_blobs`, `checkpoint_writes`). Uses single-writer advisory locking (`engine_leader`) without interference.
      2. `loopkeeper-telemetry` (`TELEMETRY_DATABASE_URL`, project `telemetry-project`, `aws-us-west-2`): High-Throughput Sensory Telemetry & Time-Series Lake. Dedicated exclusively to `world_snapshots`, `world_events`, and `sensor_samples`, plus time-window compaction, pruning, and retention policies.
      3. `test-scratch` Branch (`br-sparkling-leaf-ar2xqgxs` on `loopkeeper-control`): Isolated disposable branch for CI/pytest runs, preventing test suites from dirtying production or live baseline tables.
    - **Implementation Details (`postgres.py`)**:
      - `PostgresStorage` maintains two distinct `ConnectionPool` instances: `self.pool` (control) and `self.telemetry_pool` (telemetry).
      - `commit(b: CommitBatch)` splits transactions atomically across both pools: control batches execute against `self.pool`, while sensory telemetry batches execute against `self.telemetry_pool`.
      - Foreign Key Integrity: Because telemetry tables (`sensor_samples`, `world_snapshots`, `world_events`) reference `simulation_runs(run_id)` and `facilities(id)`, `register_facility`, `create_run`, `update_run`, and `fork_run` mirror run headers across both databases automatically.
      - Query Routing: Control reads (`load_run`, `load_commands`, `load_incidents`, `load_leases`) read from `self.pool`. Telemetry reads (`load_sensor_samples`, `list_snapshots`, `get_snapshot`, `latest_snapshot`, `load_events`) read from `self.telemetry_pool`, with graceful zero-downtime fallback to `self.pool` if `TELEMETRY_DATABASE_URL` is unconfigured.
96. **Concurrent Maintenance & Zone-Lock Collision Handling**:
    - **Problem**: In soak tests where all six fault kinds are injected simultaneously (`test_all_six_faults_injected_at_once_like_the_live_demo[3-2.0]`), `INC-001` (`valve_stuck` on `valve_a2`) previously escalated because `INC-004` simultaneously dispatched crawler `IR-03` on an inpipe bore inspection across header `p_hs_a` (holding shared engine lock `zone:zone_a`), while `INC-001`'s OUTRIG `service_valve` requested an exclusive lock `zone:zone_a`. When `dispatch_and_wait` was refused with `resource_locked: zone:zone_a held by m_004_insp0`, `outrig.py` immediately failed the work order, treating a transient lock wait as a failed repair attempt and burning all `max_replans` retries before the inspection crawler finished.
    - **Fix**:
      1. In `outrig.py`'s `prepare`, the state machine now explicitly awaits engine zone and asset lock clearance (`ctx.engine.locks.conflicts(f"zone:{z}", s.id, True) is None`) alongside physical crawler departure before proceeding to rack cordoning and workload migration.
      2. In `outrig.py`'s `execute`, lock readiness is checked prior to dispatch, and bounded simulation-time retries are performed upon encountering `resource_locked` responses rather than prematurely exhausting repair attempts.
    - **Verification**: All 3 parameterized soak test instances (`[3-2.0]`, `[3-12.0]`, `[8-12.0]`) pass cleanly (100% resolution, 0 escalations).
